物联网的背景和我们的关注点

物联网（Internet of Things，简称IoT）是物理设备的网络，这些设备包括电器、智能手机、车辆、路灯、基础设施元件、工业机器等等，它们也被称为 “事物”（物联网中 “T” 的含义）。

凯文·阿什顿（Kevin Ashton）在宝洁公司工作时创造了 “物联网” 这个术语（尽管他更喜欢 “为事物的互联网” 这一表述）。起初，它只是一项借助RFID标签识别物理对象（即事物），并在软件系统中利用相关信息的实践。从那以后，情况发生了很大变化。许多变革和理念共同将物联网的范畴拓展得更为广泛。如今，物联网是一个融合了多种元素的体系，包括具有一定计算能力和内置智能的物理对象、使这些对象能够连接到互联网生态系统的媒介，以及整个互联网的计算机制，其范围涵盖从用户设备到计算机的各个层面。

从物联网平台的角度来看，我们关注的重点是物理对象首次接入互联网的环节，以及在软件和应用接管之前发生的关键过程。这些平台通常被称为中间件软件，因为它们处于物理对象和数字系统这两个不同事物的中间位置。中间件通常融合了高级和低级逻辑，并且结合了高级和低级语言来完成任务。

需要注意的是，我们并不打算构建一个功能完备、企业级的物联网平台。相反，我们将采用敏捷的方式，专注于在不投入大量资金的前提下缩短产品上市时间。我们的目标是设计出一个能够逐步扩展的平台，在扩展过程中无需进行大量返工，也不会对当前的工作状态造成潜在干扰。

虽然对于什么可被称为物联网平台并没有严格的定义，但人们普遍期望平台能够帮助高级软件、应用和系统与低级协议、通信方法以及各种异构对象进行交互。这种宽泛的定义或理解意味着符合这一标准的事物繁多。物联网平台是整个物联网生态系统的重要组成部分，但由于营销噱头和供应商的大量涌现，这个术语变得相当令人困惑。

市面上有多少种平台？

如今，市面上有超过500种不同类型和规模的平台，而且这个数字还在不断增长。有趣的是，许多平台正逐渐失去吸引力，它们要么停止运营，要么与其他平台合并。与此同时，一些平台正演变得更具前瞻性和强大功能。简而言之，这一领域的变化是双向的。

对这些平台进行概述后，我们可以将它们分为三大核心类型。

  • 支持网络服务的平台：这些平台支持网络服务部分，如MAC层通信解码器和转换器，主要控制和协调事物的电信部分。例如，LoRaWAN通信的网络服务器，这类平台将无线电级别的通信转换为原始数据信息，并将其传递给上游平台或应用进行进一步处理。除了网络服务平台，还有一些其他部分，如身份和密钥管理服务，以及它们的组合。

  • 位于网络和应用之间的平台：这些平台支持网络层之后、应用层之前的处理工作，例如系统级协议解码、转换、解密等。它们能够控制和协调协议以及整体通信流程，还支持驱动级逻辑和依赖它们的整个系统的底层架构。我们可以将它们视为系统的核心基础架构，这也是我们在本书中要构建的内容。

  • 应用层开发平台：这些平台支持在云端进行高级开发，大多帮助整合多个中间件平台、其他系统（如ERP和CRM）以及类似应用。这类平台与前两类（网络和中间件平台）的区别在于，如果高级平台出现故障，其他两个平台仍可继续运行，并可能支持高级平台中仍在正常工作的部分。相反，如果网络或中间件平台出现故障，整个系统和解决方案可能会出现停机。

鉴于我们有这么多类型的平台，市场上的选择又如此之多，定义一个优秀的物联网中间件平台应具备的要素就显得非常重要。

一个好的物联网平台应该具备什么？

对于每一款产品而言，其功能和特性都可分为必备和可选两类。当我们对两者加以区分时，答案就相对明晰了，打造自己的物联网平台更具意义。对于任何一个想要成为物联网一部分的中间件平台来说，必须具备以下功能和能力：

  • 可扩展性：与任何新的应用程序或产品一样，事物通常从小规模起步，而后逐渐发展壮大。因此，如果中间件平台要成为解决方案的核心，它必须能够按相同比例进行扩展。虽然扩展并非一蹴而就，但应确保在不破坏现有功能和不干扰现有生产设置的前提下，能够相对轻松地进行平台扩展。

  • 可靠性：一般来说，作为解决方案或产品核心的任何事物都应具备可靠性，这是显而易见的期望。中间件内置的冗余程度会根据最终应用、产品或行业领域而略有不同。例如，与咖啡机等家用电器的物联网平台相比，用于医疗设备、金融服务或安全系统的物联网平台，其所需的可靠性水平相对较高。

  • 定制性：由于我们正在构建自己的平台，它可以实现100% 的定制化。即便你打算购买现成的平台，也应确保在合理成本范围内进行定制。如果无法对中间件进行定制，那么你就不得不修改自己的产品或服务以适配该平台，这实际上是一种本末倒置的做法。

  • 支持的协议和接口：从基本定义来看，物联网中间件平台位于两个异构系统之间，即物理设备和云软件（设备类型和软件种类繁多）。该平台应能够与所有这些设备和软件进行协调，统一安排各项事务，并支持所有的语言或协议。此外，它还需具备在必要时创建所需插件以填补差距的能力，这样才能确保在进行全面升级之前的很长一段时间内，中间件平台都能保持良好的兼容性。

  • 硬件无关性：物联网本质上是由一组异构的连接事物、硬件设备、计算机系统和软件组成的。因此，对硬件的无关性要求几乎是不言而喻的。之所以仍需明确指出这一点，是因为存在一种稍有偏差的观点。许多人将硬件视为传感器的电子电路，基于这种观点，我们强调物联网平台应与你在电路中使用的任何电子元件无关。无论是开源硬件设计、专有电路，还是两者的混合，平台都应能够提供支持。

  • 云无关性：与硬件无关性类似，平台还需要具备云无关性。目前有众多云服务提供商，包括谷歌、微软和亚马逊网络服务（AWS）等，但平台不应依赖于特定的云服务。无论是你自己的服务，还是运行在网络附属存储（NAS）背后的第三方云服务，平台都应能正常工作。一个简单的合规性测试是看平台能否在裸机服务器上运行。也就是说，如果你获得一个虚拟专用服务器实例并安装该平台，它是否能够正常工作？答案应该是肯定的，这就表明该物联网平台具有云无关性。

  • 架构和技术栈：清晰明确的架构以及合适的技术栈组合是区分优秀物联网平台与其他平台的关键因素。平台可能构建于一些看似不太常见的技术组合之上，而这些技术可能在未来几年内面临淘汰，尤其是在你使用的运营期间。如果是这种情况，你应该避开这样的平台。同样的道理也适用于架构，即中间件的 “基础架构”。如果架构不够灵活，无法适应未来的变化，这就是一个危险信号。然而，完全灵活的架构也并非理想之选。你需要的是一个兼具灵活性和稳定性的架构，并由可靠、高效的技术栈提供支持。

  • 安全性：在过去几年里，物联网在很多应用和解决方案中，由于安全管理不善而饱受诟病。“物联网中的S代表安全” 这句话已变得十分常见，这强烈表明了中间件平台中的安全性与物联网生态系统的其他方面同样重要。如果你选择多租户平台，安全就成为一个至关重要的考虑因素。多租户特性使系统更容易受到攻击，因为即使你自己的应用运行良好，但同一平台上的其他应用（你的应用的共同租户）可能会给其他所有租户带来安全问题，这种风险始终存在。

  • 成本：为物联网平台设定的预算对成本因素有较大影响。总体而言，如果平台的成本（无论是内部构建还是购买现成的）与其功能和特性不匹配，就必须对其进行重新评估。简而言之，平台应具备足够的价值，以证明其成本的合理性。

  • 支持：持续的平台管理支持固然至关重要，解决方案集成方面的支持同样不可或缺。作为一项强制性要求，中间件平台应在解决方案的设计、开发、部署和管理的全过程中提供有力支持。

为什么你应该打造自己的物联网平台？

随着企业的发展和工作场景的演变，我们看到许多小型公司开始涉足物联网领域。然而，没有自己的物联网平台成为了这一发展进程中的障碍之一。

为什么不使用免费增值或免费试用的平台呢？当业务规模扩大时，成本会呈指数级飙升，这将带来更大的挑战。当试用期结束或免费增值服务无法满足需求时，用户会发现自己陷入困境，难以轻易切换到其他平台。这对许多小公司来说是一个巨大的挑战，拥有自己的物联网平台则是一个更好的解决方案。

一开始，购买现成的平台或选择免费增值服务可能看起来是更好的选择，但这其中存在权衡取舍。物联网平台可能会节省你的时间，但最终成本可能更高，这取决于供应商的定价方式。这主要是因为收费方式可能基于使用量或设备数量，此外，订阅费用会随着时间累积。虽然你能享受到前期成本显著降低的好处，即无需资本支出，但这也取决于你计划如何向购买物联网产品或解决方案的终端用户或客户收费。

最初成本较低的物联网平台可能会在时间成本上让你付出代价。这又回到了同一个问题：你花费的越少，就需要自己投入更多的时间和精力来集成和管理这些平台。如果你必须花费大量时间，那么将这些时间用于打造自己的平台，难道不是更好的选择吗？

打造自己的平台还支持在起步阶段节俭行事，然后仅在必要的时间和地点进行投资的理念。这将帮助你在不超出预算的情况下利用技术进步，更重要的是，你可以快速启动项目。本书将介绍如何在24小时内构建一个物联网平台，这与适应现成的或功能齐全的平台，以及学习使用免费试用或免费增值平台所需的较长时间形成鲜明对比。

如果你非常看重完全掌控权，那么一定要打造自己的解决方案。购买现成的解决方案通常意味着你需要调整自己的需求，对解决方案进行改造以适应现有的产品。这可能导致你构建出一个质量欠佳的解决方案，甚至可能是一个糟糕的方案。而打造自己的平台可以让你完全灵活地掌控自己的需求，包括如何构建以及何时构建。

从头开始打造自己的平台始终是一次充实的学习经历，如果可能的话，不应错过这样的机会。

物联网的广泛热议出人意料地阻碍了人们对其工作原理的理解。如果你询问20个人物联网是如何工作的，可能会得到20种不同的答案。其中大多数答案可能涵盖的是物联网的成果或已实现的物联网解决方案的运作方式，而非物联网本身的工作原理。在物联网的背后，有许多技术支撑其得以实现。

这些主题将帮助我们了解物联网的整体运作机制，进而有效地规划构建自己的物联网平台。

让我们首先讨论一些经常互换使用的术语。物联网解决方案和物联网应用之间存在差异。物联网解决方案通常指的是一个端到端的产品、服务，或两者的结合；而物联网应用通常是指IT软件、移动应用，或两者的组合。显然，物联网解决方案涵盖的内容比物联网应用要多得多。许多业务背景、客户背景和地缘政治背景都会对物联网解决方案产生影响。

然而，从物联网平台的角度来看，它处于物联网应用的边缘，通常是连接物理对象（即 “事物”）和软件系统的边界系统。图2 - 1展示了一个典型物联网解决方案的架构图，它以一种清晰的方式呈现了物联网解决方案的架构，将各个组成部分按照大型系统的重要方面进行了区分。

物联网解决方案的功能模块

从高层次来看，我们可以确定物联网解决方案由四个主要功能模块组成。如果缺少其中任何一个模块，都不宜称之为物联网解决方案。

  • 设备（又称 “事物”）：是物理传感器和执行器，它们测量各种参数并将其转换为电信号或数字数据。这些传感器要么连接到主机设备（常用于传统设备升级），要么集成到主机设备中（现代设备的常见做法）。这些设备是物联网应用的关键节点，通过作为输入、输出或兼具两者的功能，来实现完整的解决方案功能。典型的设备示例包括恒温器、智能捕鼠器、联网冰箱等。

  • 网关：是边缘设备，它与上游系统的通信方式有两种：有网关或无网关。有些设备具备通过各种通信协议（如REST、MQTT、AMQP、CoAP等）直接使用互联网协议（IP）进行通信的能力。这些能力通常得益于集成的通信模块，如Wi - Fi或GSM芯片，使设备能够连接到网络网关（如Wi - Fi路由器和移动基站）并直接与上游层进行通信。在这种情况下，路由器和移动基站就起到了网关的作用。然而，并非所有设备都具备直接连接互联网的能力，也并非都内置了必要的硬件。在这些情况下，它们需要借助其他设备将数据推送到上游层，而网关就能帮助设备实现这一点。通常，硬件网关采用双通信技术构建，使其能够通过一种通道与下游设备通信，通过另一种通道与上游层通信。典型的网关功能示例包括GSM和RF、GSM和蓝牙、Wi - Fi和蓝牙、Wi - Fi和XBee、LoRaWAN和以太网等组合。在某些情况下，智能手机也可作为网关，这在蓝牙低功耗（BLE）设备中更为常见。除了提供传输机制外，网关还可以提供一些可选功能，如数据隔离、清理、聚合、去重和边缘计算。

  • 物联网平台：是整个物联网解决方案的协调者，通常托管在云端。该模块负责与下游设备进行通信，并以极高的速度摄取大量数据。平台还负责以时间序列和结构化格式存储数据，以便进一步处理和分析。根据其内置的复杂程度，平台可能支持深度数据分析和其他操作。然而，物联网平台的核心功能是作为整个系统的协调者。

  • 应用程序：在大多数情况下，是整个解决方案面向最终用户的界面，必须以有意义的方式呈现给用户。这些应用程序可以是基于桌面的、基于移动设备的，或者两者皆有。应用程序还以各种方式丰富来自平台的数据，并以可用的格式呈现给用户。此外，这些应用程序在接口层面与其他系统和应用程序进行集成，实现应用程序间的数据交换。一个典型的操作示例是配备跟踪移动应用程序的库存跟踪设备，将数据提供给用户，并将数据输入到ERP系统进行库存管理。

互连的箭头表示每个模块之间的数据和信息流。每个模块都代表了平台的主要功能组件。该平台安装在虚拟云机器或虚拟专用服务器（VPS）上。强烈建议使用基于Linux的操作系统，如Ubuntu、Centos、Debian、OpenWRT或LEDE，以获得更好的性能、安全特性和对平台的整体控制。无论使用这些操作系统中的哪一种，其概念和模块级架构都不会改变。

  • 边缘接口、消息代理和消息总线：该模块负责与物理世界进行交互，尤其是与异构设备和传感器进行通信。由于设备可能通过多种通信技术（如Wi - Fi、蓝牙、LoRaWAN、GPRS等）进行通信，因此该模块需要支持所有这些技术。我们可以采用模块化的方式来实现这一点，即分别处理每种类型的通信协议。例如，支持Wi - Fi的设备可以通过REST API进行通信，适用于受限设备；也可以采用基于MQTT的消息代理，以发布/订阅的方式实现通信。对于基于LoRaWAN（长距离广域网）的设备，主消息代理有一个额外的插件，用于与LoRaWAN网络服务器进行通信并对数据包进行解码。

    注意，发布/订阅（pub - sub）指的是通信的发布 - 订阅范式，将在第6章中详细解释。

    该模块有效地将整个平台与设备解耦，支持现代物联网设备的多种边缘接口和协议。无论使用何种通信介质、网络类型和协议，消息代理的任务都是以统一的方式整合数据，并将其推送到公共消息总线。所有其他功能模块都通过这个消息总线进行进一步的操作。消息代理起到消息协调者和整合者的作用。

  • 消息路由器和通信管理：一旦消息出现在主消息总线上，可能需要添加更多上下文信息或进行优化，以便其他模块使用。有些消息需要进行功能增强和添加额外信息，这取决于设备部署的上下文和应用程序的要求。通信管理模块负责对现有数据消息进行功能增强、重新广播到消息总线、在主消息到达后发布额外的上下文信息和其他消息，并进行适当的标记。通信管理功能与消息代理和规则引擎模块进行协调，并根据需要与设备管理器进行交互。

    此外，通信管理模块还执行格式转换任务，例如将数据从CSV转换为JSON，或从二进制转换为文本格式等。我们还可以让它执行一些操作，如消息去重。去重是指从设备中消除或丢弃多个重复消息或冗余数据包的过程，因为它们可能没有任何用处。去重方案取决于设备或传感器的类型，我们需要根据具体情况进行实施，尽管方法是相同的。作为通信路由器，该模块可以控制平台上的进一步消息传递和通信。

  • 时间序列存储和数据管理：顾名思义，该模块按顺序（即时间序列方式）存储消息总线上接收到的所有已解析数据。虽然数据存储不是物联网平台的核心功能，平台外部的模块也可以处理存储，但从协调和编排的角度来看，这是一项必不可少的活动。通常，通信和路由模块，甚至消息代理本身，出于特定功能目的需要近期数据，此时这种存储就派上了用场。对于许多物联网应用，用户更倾向于将数据从物联网平台中提取出来，存储在应用数据仓库中进行进一步处理。因此，它通常用于临时存储设备数据，并不适合存储大型数据集。

  • 规则引擎：在我看来，这是一个非常强大的模块，它为平台提供了增强的功能。规则引擎是一个执行模块，它监控消息总线和平台上的事件，并根据设定的规则采取行动。例如，一个典型的规则引擎功能可能是：“当下游设备发送包含‘ka - boom’关键字的数据包时，触发并广播警报消息”。规则引擎持续监听消息总线的广播。当通信模块将来自下游设备的解码数据包发送到消息总线上时，规则就会触发。然后，规则引擎向消息总线广播另一条消息（警报）。由于这一切都在物联网平台内部以及紧密协作的模块之间发生，因此执行速度非常快。规则引擎还有助于构建用于解码和丰富从设备接收的现有数据的模块化规则，从而增强通信模块的功能。此外，很容易实现对其他模块、应用程序、程序和系统的回调。

  • REST API接口：RESTful API对于那些不需要持续或实时连接和访问的支持功能和实用程序非常有用。虽然通常由上游程序和应用程序使用，但下游设备在需要时也可以访问这些API。一个典型的用例是具有Wi - Fi连接的温度传感器，它每15分钟发送一次读数。由于两次读数之间的时间间隔较长，因此不需要实时连接或始终保持连接状态。简单的HTTP操作就可以相对更高效地完成数据发送任务。在这种情况下，传感器可以通过REST API将数据发送到平台。REST API与消息代理和通信管理器协同工作，将接收到的数据发布到主消息总线上；它还可以使用时间序列数据库记录向传感器发送响应。这个响应可能包含一些额外信息，以便传感器在下次工作时能够以特定方式运行。该API模块还支持数据聚合和批量操作功能，例如上游应用程序查询多条记录。通过这种方式，上游应用程序和系统与核心平台模块保持解耦，从而维持功能的划分并确保安全性。可以构建各种基于角色的认证机制来访问API。REST API模块还可以与规则引擎交互，允许应用程序在任何给定时间配置或触发特定规则。这也使得下游设备能够使用相同的功能，当设备需要自动启动某些工作流程而不是由应用程序触发时，这一功能会非常方便。例如智能锁，当前门有活动需要房主注意，而房主不在家时，上游应用程序可能会在智能锁报告活动时通知用户，然后等待用户响应或采取进一步行动。如果用户无法响应，应用程序可以触发预定义操作的规则。如果警报的严重程度较高，设备可以配置为不等待用户操作或响应，而是直接触发默认工作流程（例如通知安保人员等）。这些功能在设计和运营自主智能设备群时非常实用。

  • 微服务：除了数据管理、操作和交换功能外，物联网平台还需要一些支持功能才能有效运行。诸如短信或电子邮件通知、验证、验证码、社交媒体认证或支付服务集成等服务，都是这些辅助服务的示例。这些服务被整合在微服务模块中。如果平台内经常使用某些功能，可以将其打包并分离到这个模块中，使其与主流平台区分开来。分离和打包后，这些功能可以在平台内部和外部的模块中进行复用。

  • 设备管理器：当平台开始托管大约50个或更多设备时，管理工作可能会变得困难。此时，有必要建立某种中央控制机制来管理设备。这就是设备管理器模块发挥作用的地方。它主要提供将设备作为资产进行管理的通用功能，包括列出所有设备、它们的活动/非活动状态、电池电量、网络状况、访问密钥、读数、存储数据访问、设备详细信息、会话信息等类似内容。设备管理器还帮助管理一批设备的无线更新，或为系统管理员提供中央监控功能。在某些用例中，设备需要访问权限，并且用户可能被分配对一组设备的特定访问权限。有了设备管理器，管理这种访问权限矩阵就变得容易了。

  • 应用和用户管理：该模块提供与设备管理器类似的功能，不同之处在于它为上游应用程序和用户提供服务。典型的用户管理功能，如密码和凭据、访问密钥、登录和权限等，都通过这个模块进行管理。对于上游应用程序和各种其他集成系统，API密钥、凭据和访问权限也可以通过同一模块进行管理。虽然这看起来更像是应用程序级别的功能，但将其作为物联网平台的一项功能进行绑定，有助于将其与整体架构紧密集成。物联网是一个系统的集合，异构系统是其特点之一。我们最不希望看到的就是这些系统功能不同步。

这个架构中的所有模块都是必需的吗？

不是的。虽然这八个模块定义了一个架构良好的物联网平台，但并非所有模块都是必需的。特定的用例或行业领域可能会对此有不同的定义。在平台开发的初始阶段，你可能不需要所有模块，它们可以在平台开发生命周期的后期添加。

核心功能模块，即设备接口和消息代理、消息路由器和通信模块、数据存储、设备管理和规则引擎，对于物联网平台的有效运行至关重要。其他模块，如REST API、微服务以及应用和用户管理，虽然很实用，通常能让工作更轻松，但并非必需，也不会妨碍物联网平台的功能。

在从头开始开发我们的物联网平台时，我们会暂时搁置这些功能，只有在时间和资源允许的情况下才会实现它们。

建议的方法

为了在最短的时间内开发出物联网平台，我们不仅要以模块化的方式进行开发，还要采用敏捷的方法。每个模块都将规划好功能和特性，进行开发，然后部署到云端进行测试。一旦我们测试了单个模块并确认其按预期工作，就可以进入下一个模块的开发。

第一步，我们将为平台搭建云环境。接下来，设置开发第一个模块（边缘接口和消息代理）所需的基本组件。逻辑上的下一步是设置时间序列数据存储。然后，我们将为平台开发基本的REST API，接着开发消息路由器功能。

在搭建好平台的基本框架后，我们将开发一些微服务。之后，我们会多次迭代这些模块，为平台打造一个稳定的核心。

一旦我们对核心功能感到满意，就可以设置规则引擎，然后是设备管理功能。由于应用和用户管理属于非必要模块，我们会在最后对其进行评估。

在开始构建平台的核心工作之前，打下坚实的基础非常重要。这不仅能让我们的平台在长期内具备可扩展性和稳定性，还有助于我们清晰地阐明当前和未来的技术需求。在本章中，我们将：

确定云实例的具体规格

要构建自己的平台，我们至少需要一个裸金属云实例。虽然在这类实例中有多种操作系统可供选择，但最推荐的是基于Linux的操作系统。让我们来看看它为何是首选。

  • 总体拥有成本：最明显的优势是Linux是免费的，而Windows不是。单个用户许可证的成本可能不高，但随着时间推移，总体拥有成本会更高，从而增加持续运营成本。

  • 可靠性：基于Linux的系统比Windows更可靠。传统上，Linux系统以能够连续运行数年而无需重启著称。这是为我们的物联网平台选择操作系统的关键标准。

  • 硬件资源：与Windows相比，Linux系统消耗的系统资源（如RAM、磁盘空间等）更少。对于我们的物联网平台，我们至少需要1GB的RAM和20 - 25GB的磁盘空间。也就是说，如果选择基于Linux的系统，成本能够得到控制。而Windows系统在这样的配置下可能无法高效运行。

  • 安全性：基于Linux的系统在设计之初就考虑了安全性，是更安全环境的首选。由于其固有的安全性，我们可以节省防病毒软件的成本和额外的系统开销。

  • 控制权：控制权是构建自己的物联网平台的主要原因之一。基于Linux的系统在各个层面都提供了控制权。没有臃肿的软件对像我们平台这样追求速度的系统来说非常重要。能够控制安装的内容有助于我们牢牢掌握这种控制权。

  • 功耗：目前，Windows只能在不符合低功耗要求的设备上运行，而我们的系统通常需要经常或始终保持运行状态，对低功耗有一定需求。

其他规格

为了保证基本功能的有效运行，我们在操作系统上至少需要1GB的RAM和20 - 25GB的磁盘空间。我们还需要Node.js和Node - RED软件来编写平台代码。

对于基于Linux的系统，我们需要在系统上安装LAMP栈。LAMP栈是一组用于创建网站和Web应用程序的开源软件，是Linux - Apache - MySQL - PHP的首字母缩写，它由Linux操作系统、Apache HTTP服务器、MySQL关系数据库管理系统和PHP编程语言组成。

除了这些基本软件包，我们还需要一些附加组件，随着进程的推进，我们会列出这些组件。一旦我们的实例安装并运行了LAMP栈、Node.js和Node - RED，就具备了继续进行的基本基础设施。

从哪里获取云实例？

在虚拟专用服务器上创建云实例有不少选择，如AWS（亚马逊网络服务）、谷歌云、阿里云和DigitalOcean等，而且可能很快还会出现更多选择。

选择哪个供应商的云实例取决于你的供应商偏好、这些供应商提供的实例定价以及许多其他因素。在很多方面，DigitalOcean似乎是个不错的选择，主要是因为它提供了简洁明了的用户界面，没有过多不必要的选项和选择干扰。这是保持敏捷并快速完成任务的关键。

从经济实惠的角度来看，DigitalOcean显然是最佳选择，因为与其他供应商复杂的毫秒级计算定价相比，它的定价透明。其价格基于按小时计费，并且通常在每月使用的情况下是固定的。

DigitalOcean不像AWS或谷歌云那样是托管服务，但这对我们的目的来说应该没问题。DigitalOcean服务器上的云实例需要由所有者自行管理，包括升级和打补丁等，而AWS和谷歌云则不是这样。然而，在处理裸金属云实例时，情况并非那么简单，所以即使使用谷歌云和AWS，如果是裸金属实例，你也必须自行管理系统。

简而言之，如果你有大规模的实施需求，应该选择AWS或谷歌云；对于其他所有目的，DigitalOcean是更好的选择。

对于我们的平台，我们追求敏捷性（即在24小时内构建完成）、成本效益、计费透明度、完全控制权以及其他类似方面。所以在本书中，我们将使用DigitalOcean作为我们的云实例。不过，如果你对其他供应商更熟悉，也完全没问题。

我们自己的机器呢？

虽然我们大部分工作会在云实例中完成，并且大部分开发也会在云环境中进行，但我们仍然需要在本地机器（笔记本电脑或台式机）上安装一些工具。

一开始，我们至少需要三种工具/软件。

  • 用于SSH的终端模拟器：我们将使用一个名为PuTTY的程序，它是一款知名且广泛使用的终端模拟器。它是一个免费的开源程序，支持多种网络协议，包括SSH、SCP、Telnet等，还允许进行原始套接字连接，并且可以连接到计算机的串行端口，这在测试我们平台上的一些硬件模块时可能会派上用场。

  • 基本编辑器：这个编辑器可以像Notepad程序一样基础，我推荐Notepad++。它是一款用于Microsoft Windows的免费软件文本编辑器，支持在单个窗口中处理多个打开的文件，非常方便。该项目的名称来源于C语言中的增量运算符。

  • FTP程序：FTP应用程序有多种选择，包括WinSCP、FileZilla、CoreFTP和FireFTP等。在本书中，我们将一直使用FileZilla。

PuTTY、Notepad++和FileZilla对我们的目的来说很有效且适用，但它们不是必需的。你可以自由选择其他可用的选项。

详细阐述物联网平台架构图

在第2章中，我们讨论了物联网平台的详细架构图。现在我们将确定哪些模块需要优先进行快速开发，以及在第一阶段需要开发哪些功能。

  • 边缘接口、消息代理和消息总线：这将是我们物联网平台的基本功能，我们会在一开始就着手开发。我们将使用MQTT协议进行消息交换，因为MQTT几乎是边缘设备和物联网应用通信的事实上的标准协议，我们稍后会详细讨论MQTT。这将是我们物联网平台最关键的模块之一。

  • 消息路由器和通信管理：一开始，我们将只开发一个基本的消息路由器，它不会具备主要的通信管理功能。我们将把这个模块作为开发第二阶段的占位符。

  • 时间序列存储和数据管理：如前一章所述，这不是核心功能，但它是我们在第一阶段要构建以便后续使用的元素之一。

  • REST API接口：为了测试从设备到平台以及从Web应用程序到平台的功能，REST API是必不可少的。我们将从基本的API开始，然后在后续阶段添加复杂的功能。

  • 微服务：虽然我们要到第二阶段才会开发微服务，但我们会提前做一些准备工作，以确保在后期添加微服务时，无需对基本设计进行重大更改。从设计上讲，微服务在物联网平台中并非关键部分。

  • 规则引擎：由于这是物联网平台最强大的功能之一，我们从一开始就要重视它。规则引擎无法一蹴而就，我们需要多次迭代才能使其完善。

  • 设备管理器和应用管理器：虽然这些功能很实用，但它们不是平台的核心部分，所以我们不会为我们的物联网平台开发这些功能。实际上，在没有正式的设备管理器和应用管理器的情况下，也可以轻松使用大量设备和应用。

与平台实时连接

Web应用程序面临的挑战之一是实时通信能力。虽然同步通信很常见，并且我们可以通过典型的类似HTTP的请求来实现，但使用相同的格式和技术无法有效地实现异步通信。然而，与物联网平台进行实时连接和通信是物联网解决方案和应用的关键要求。这就是我们需要使用消息代理并实现类似发布 - 订阅机制的原因。

这也是消息代理成为最新Web技术重要组件的关键原因。消息代理通常是中间件程序，借助发布 - 订阅机制为所有连接的应用程序和设备提供异步通信能力。

发布 - 订阅机制是一种有趣的范式，它不要求通信双方同时在线。此外，它还使得任何一方都可以在不考虑对方是否准备好的情况下发起数据传输。这与HTTP的工作方式完全相反，在HTTP中，客户端必须发起请求，服务器才会响应，服务器无法实时联系客户端。当我们通过消息代理使用发布 - 订阅机制连接服务器和客户端时，双方都可以发送数据，这是一项强大的功能。

简而言之，我们需要一个消息代理程序。选择的消息代理必须满足某些基本标准，一般来说，两个重要标准是易于配置和维护，以及在生产环境中足够稳定。

使用MQTT作为消息代理

虽然消息代理技术有很多种，但我们将使用MQTT标准，因为它几乎是物联网应用和解决方案的事实标准协议。

MQTT代表MQ遥测传输，是一种发布 - 订阅、极其简单且轻量级的消息传递协议，专为受限设备以及低带宽、高延迟或不可靠的网络而设计。其设计原则是在确保可靠性和交付保证的同时，尽量减少网络带宽和设备资源需求。这些原则使该协议非常适合新兴的机器对机器（M2M）或物联网连接设备领域，以及对带宽和电池电量要求较高的移动应用（mqtt.org，2013）。

MQTT有许多实现方式，包括商业版和开源版。Mosquitto是一个流行的开源MQTT实现，我们将使用它来构建我们的消息代理。我们也可以使用任何其他基于Node.js的MQTT开源实现来构建消息代理，以后可以探索这个选项，它可用作我们平台冗余的备用二级代理。

我们希望如何存储数据？

到目前为止，我们已决定使用Mosquitto作为MQTT消息代理。然而，消息代理不是存储提供商，它们更像是消息传递的载体，消息或数据通过它们传递。这些数据是临时的，如果不存储，以后就无法查看或检索。

从平台的角度来看，我们需要这种存储和检索机制，以便能够在以后检索数据；对于非同步的应用程序和设备，这些数据可以作为信息的影子副本。

由于我们在安装了LAMP栈的Ubuntu服务器上构建平台，MySQL是默认且明显的选择。不仅如此，根据2018年DB - Engines排名，MySQL一直是第二受欢迎的数据库。

关键问题是我们希望如何存储数据。这里所说的数据是指通过消息代理和中央消息总线通信管理器的事务数据。这些数据只有几个用于数据处理和审计目的的信息字段，因此，我们的数据存储模式必须适合这些数据。

在MQTT通信中，每个消息数据包都包含两个字段：主题（topic）和有效负载（payload）。主题通常用作数据的键，而有效负载是实际的数据或内容。由于MQTT是一种消息传递协议，并不一定指定有效负载的格式，所以我们有一定的灵活性。然而，为了在整个平台上保持可扩展性和统一的方法，我们将在整个平台上对有效负载（即数据包）使用JSON（JavaScript对象表示法）编码。这不仅有助于保持一致性，还将使我们的平台具有可扩展性，并且易于适应新的变化。

数据存储模式

JSON数据本质上是一个ASCII字符串，也是MQTT消息中的主题。需要注意的是，MQTT也支持二进制数据包，其中可能包含非ASCII字符。这意味着我们可以轻松通过消息代理传输二进制文件和数据，在设计平台时应牢记这一点。

除了存储主题和相关的数据有效负载外，我们还需要为存储的每条消息分配一个唯一ID。最重要的是，由于这将是一个时间序列数据库，我们需要存储每条消息的时间戳。在这个阶段，除了这些字段，我们在物联网平台的核心中不需要存储任何其他信息。基于这些考虑，我们的数据库表结构如图4 - 1所示。

以下是对每列的简要解释：

  • ID：自增唯一编号，我们使用MySQL的自动递增功能来实现。

  • Topic：声明为varchar类型，以便在该字段中存储可变长度的数据。主题的长度可以任意，并且根据应用程序的不同而变化。我们将限制其长度为1KB，这对于任何可能的主题名称来说都足够大。

  • Payload：数据包的大小较大且长度可变（因此使用可变类型）。不过，目前我们将数据包存储限制为2KB。请记住，这些是MySQL的可配置选项，可以在不影响应用程序的情况下进行更改。我们可以增加大小限制而不影响先前存储的数据，但降低大小时，先前的数据可能会被截断，这可以根据需要决定。

  • Timestamp：我们将存储UNIX（即基于纪元的时间戳），它是UNIX风格的日期时间戳，以整数格式表示。纪元（或UNIX时间、POSIX时间、UNIX时间戳）是自1970年1月1日（午夜UTC/GMT）以来经过的秒数，这里不考虑闰秒。这可能不是一个精确的时间戳，但对于现实场景来说已经足够接近，满足我们的应用目的。

基于这个表结构，我们将把接收到的每个数据包存储在Payload列中，并将其主题存储在Topic列中，两者均按原样存储。时间戳将取自我们平台的系统时间，ID将自动递增。这将使我们能够在需要时按存储顺序并参考时间戳查询数据，使其成为一个时间序列数据集。

通过API访问平台资源

有了Mosquitto MQTT代理和时间序列存储后，我们的平台一般就能接收数据包并通过MQTT进行通信。这种（通过MQTT的）通信将基于数据流，如果没有平台的其他部分，不一定具备任何内置智能。

连接到数据流的设备或应用程序能够实时访问数据，但在离线或未连接时，没有机制来请求数据。这就是我们的API将发挥重要作用的地方。

在计算机编程领域，API指应用程序编程接口，它是一组子程序或子过程定义、通信协议和用于构建软件的工具。一般来说，它是一组明确定义的计算机程序或系统各组件之间的通信方法。一个好的API通过提供所有构建模块，使程序员能够为实现特定目的将它们组合在一起，从而更轻松地开发计算机程序。

让我们将API分为四种不同类型，这将有助于我们保持开发的模块化和可插拔性。

  • 数据访问API：这些API帮助我们访问物联网平台中的时间序列数据存储，并进行有限的操作。此外，该API有助于在实时数据流（基于MQTT）和非实时数据流（基于HTTP）之间建立链接。

  • 实用工具API：许多应用程序在非定期基础上可能需要某些实用工具。这些实用工具的一个典型示例是特定格式的数据转换。如果应用程序或设备需要一次性对数据进行编码或加密，或者需要在特定条件下对其进行转换，那么它可以使用其中一些API。本质上，它们是平台内外多个资源共享的封装函数。

  • 微服务API：基于功能或服务于特定预定义目的的端点属于这一组。这些通常是应用服务，如电子邮件和短信服务。

  • 插件API：我们构建的一些接口将连接平台中原本未连接的两个部分。其中一些API还充当移动或计算机应用程序的前端。

数据访问API

为了安全、适当地访问时间序列数据，我们将设计一组API以满足各种场景和需求。一般来说，我们至少需要七个端点。注意，每个需求都进行了编号，以便我们在本书中轻松引用。数据需求以D开头，而微服务和实用工具需求以M开头。

  • D1. 获取单个数据记录：使应用程序和设备能够根据指定的主题或主题模式从时间序列数据存储中查询单个数据记录。

  • D2. 按序列获取多个数据记录：使应用程序和设备能够根据指定的主题或主题模式查询多个数据记录。

  • D3. 根据特定条件获取一个或多个记录：使应用程序能够根据指定条件（针对主题、有效负载或两者）查询一个或多个数据记录。条件可以是主题或有效负载模式，或者与时间戳相关，例如某个时间段内的数据。

  • D4. 通过API存储数据记录（如果未通过MQTT流发送）：除了从时间序列存储中查询数据外，我们还希望应用程序和设备能够将数据存储在时间序列存储中。这对于无法通过实时MQTT数据流进行通信的设备和应用程序很有用。

  • D5. 删除单个数据记录：使应用程序或设备能够根据指定主题删除单个数据记录。请注意，我们不希望实现主题模式机制，以避免意外的数据清除。

  • D6. 按序列删除多个数据记录：从数据集中删除基于主题的一组数据记录。如果我们希望保持数据存储的精简，这很有用。此需求的一个典型场景是删除24小时后的所有数据，或者结合多记录查询，将数据从平台存储中取出并存储在其他地方用于审计或监管目的。

  • D7. 根据特定条件删除一个或多个记录：与根据指定条件查询一个或多个数据记录类似，我们可能需要从时间序列存储中删除它们。虽然这是一个有用的功能，但它需要内置一定的安全级别，我们将详细讨论这一点。

基本微服务和实用工具

这里我们列出一些希望在物联网平台上经常（但不频繁）使用的微服务和实用工具。

  • M1. 发布当前时间戳：我强烈推荐在分布式应用程序中使用此服务。我们经常发现，由于时区差异和系统时钟限制，系统之间无法协调。我们可以借助时间广播服务来克服这个问题。另一种替代方法是使用NTP（网络时间协议），但并非所有应用程序或设备都能访问NTP服务器，这限制了它们进行时间同步操作的能力。我们将使用此实用工具从我们自己的物联网平台发布/广播时间值，以便所有系统都与我们的平台同步。我们可以单独将平台与NTP服务器同步，无论如何，我们的平台都提供了一个稳定的参考源。

  • M2. 获取当前时间戳：这是发布当前时间戳功能的轮询服务。当设备或应用程序错过先前的时间戳广播且无法等到下一次广播，或者用户或业务规则强制设备或应用程序进行同步时，此服务很有帮助。

  • M3. 获取唯一或随机数/字符串：这是一个非常方便的服务，用于生成和使用随机字符串和数字。我们可以使用随机生成的数字和字符串创建唯一键或参考编号，也可以将它们用作随机密码或令牌。

  • M4. 获取UUID：UUID（通用唯一识别码）类似于随机数或字符串生成服务，但更具结构性且在全球范围内唯一。UUID算法保证在公元3400年（即从现在起1500年后）之前生成的任何UUID都极有可能与其他UUID不同。与随机字符串类似，我们可以使用UUID为设备和应用程序生成密钥或密码。

  • M5. 发送电子邮件：这是许多应用程序和平台可能经常使用的普遍服务。我们需要电子邮件服务用于自动化、警报、用户检查和验证、密码重置、关键通信等。这是我们物联网平台必备的服务。

  • M6. 发送短信：我们可以将短信用于与电子邮件类似的目的。此外，我们还可以在需要额外安全层的系统或关键部分中使用它来实现双因素身份验证。我们的应用程序和连接到平台的其他应用程序都可以使用此服务。

  • M7. MQTT回调注册：由于MQTT数据馈送是实时的，对于仅依赖HTTP机制的应用程序而言，除非应用程序持续或频繁轮询，否则无法收到新数据可用的通知。为避免这种情况，我们开发了一种服务，本质上是创建一个Webhook，每当平台接收到与给定主题或有效负载标准匹配的数据包时使用。这样，仅使用HTTP的应用程序可以通过REST API（如D4中所述）发送或传输数据包，并通过此服务接收（得到通知）。我们可能需要利用规则引擎来编写此服务。请注意，此服务仅适用于基于服务器的应用程序，硬件设备不太可能从中受益。

什么是MQTT？

MQTT是一种客户端 - 服务器发布/订阅消息传输协议。它具有轻量级、开放、简单且易于实现的特点。这些特性使其非常适合在许多场景中使用，尤其适用于诸如机器对机器（M2M）和物联网（IoT）等受限环境，在这些环境中，对代码占用空间要求较小，并且/或者网络带宽十分宝贵（OASIS标准 - MQTT版本3.1.1，2015）。

MQTT是一种非常轻量级的二进制协议，由于数据包开销极小，因此很容易在受限设备上实现，这使其成为物联网设备（即 “事物”）的理想选择。

发布和订阅范式

与使用客户端 - 服务器架构的HTTP交互类似，MQTT采用发布/订阅架构。作为其内在要求，它需要在中间设置一个消息代理。这实际上将发布者（或发送客户端）与订阅者（或接收客户端）解耦。此外，这也意味着我们可以有多个订阅者订阅同一发布的消息。

让我们通过一个简单的示例来了解发布和订阅范式的工作原理，如图6 - 1所示。有五个客户端（即 “事物”）通过互联网连接到消息代理，每个客户端都扮演着不同的角色：

  • 客户端A和B是传感器设备，分别传输温度和湿度数据。

  • 客户端C是一台联网风扇。

  • 客户端D是一台笔记本电脑。

  • 客户端E是一个移动应用程序。

由于客户端C、D和E需要根据A和B发布的信息采取行动，所以它们是温度和湿度信息（主题）的订阅者。传感器客户端A和B会定期在各自的通道（主题）上传输温度和湿度数据（有效载荷）。消息代理负责跟踪哪些客户端已连接以及它们订阅了哪些主题。

每当客户端A和B发布信息时，客户端C、D和E就会收到这些信息。

发布/订阅范式的优点在于，即使其中一个客户端出现故障，也不会导致系统崩溃。消息代理在多个层面上帮助解耦客户端，使它们无需同时与代理保持连接，也无需进行时间同步。

发布/订阅机制还使我们能够实现更好的消息路由和基于事件的操作。这对我们的物联网平台非常重要，因为它可以改善整体架构并使其更加清晰。架构的可扩展性是我们在平台上使用MQTT和发布/订阅的另一个重要原因。

作为独立的客户端，系统中的每个节点都可以将其信息贡献到更大的生态系统中。这意味着我们可以让风扇C根据客户端A和B的读数，以及图外其他温度传感器（例如天气预报或环境监测系统）的读数来采取行动。

消息代理和MQTT的其他特性

一般来说，术语 “客户端” 指的是所有连接到MQTT消息代理或通过它进行通信的设备或应用程序。因此，客户端可以是信息的发布者、订阅者，或者既是发布者又是订阅者。由于MQTT是基于TCP/IP的协议，任何能够使用TCP/IP进行通信的设备都应该能够建立MQTT连接并成为客户端。在实际应用中，可能会存在一些限制因素，但该协议本身就是为在受限设备上使用而设计的。

我们可以将传感器和控制系统设备视为客户端；同样，其他计算机、移动电话或Web应用程序也可以作为客户端和/或传感器。所有这些以有意义的方式组合在一起，最终形成一个可用的解决方案。

另一方面，消息代理是这种通信的协调者或组织者。它的职责是接收来自所有客户端的消息，对其进行过滤，查找哪些客户端订阅了哪些主题，然后将消息重新分发给这些客户端。消息代理还负责维护各种连接参数，例如客户端会话详细信息、凭据、存储的（即保留的）消息数据库以及其他一些信息。

由于消息代理在发布/订阅通信系统中扮演着如此重要的角色，因此它应该具有高可用性、容错性，易于部署、监控和维护，并且易于与整个解决方案的其他多个方面进行集成。我们选择的代理Mosquitto满足所有这些标准。

服务质量

在发布/订阅机制中有一个有趣的概念，称为QoS（Quality of Service，服务质量），它是MQTT通信中一个关键且非常有用的特性。尽管MQTT协议本身轻量级且简洁，但它使客户端能够与代理长时间保持稳定的连接，并确保所有发布或订阅的消息都能在一定程度上得到传递保证。这种保证通过MQTT消息的 “QoS” 来实现。

QoS是消息发送方和接收方之间的一种约定。需要注意的是，就发布/订阅机制而言，至少存在两个发送方和两个接收方，因为每条消息都要经过代理。因此，对于任何发送的消息，代理是第一个接收方，然后才是后续的接收方，反之亦然。所以，在MQTT环境中，QoS在这两个层面上起作用。

MQTT支持三种QoS级别：

  • QoS 0：最多一次（也称为 “即发即弃”），意味着消息可能会丢失。

  • QoS 1：至少一次（即可能会有重复消息）。

  • QoS 2：恰好一次。

有时，订阅者的QoS级别可能与发布者的QoS级别不同。例如，发布者以精确发送一次（QoS 2）的意图发送消息，但如果订阅者对这种确定性要求不高，它可以以QoS 0级别订阅该消息。因此，当代理尝试将此消息传递给订阅者时，QoS会根据订阅者的要求进行降级。相反，如果订阅者要求的服务级别高于发布者，QoS也会升级到订阅者要求的级别。

QoS机制有助于选择合适的通信服务级别，以匹配客户端的运行环境。例如，如果客户端处于通信环境不太可靠的移动车辆中（通过3G连接），那么这些客户端可以选择更高的QoS级别以确保接收到通信内容。而在家庭中通过Wi-Fi连接的客户端，由于连接可靠性较高，可以选择较低的QoS级别。

一般来说，当连接可靠且丢失一条或多条消息不会造成任何问题时，应选择QoS 0。QoS 1通常是最佳选择，因为消息至少会被接收一次，并且如果接收到重复消息，可以在应用层进行处理。如果每条消息都至关重要，绝对不能跳过或遗漏，则强烈建议使用QoS 2。需要注意的是，我们始终可以在应用层实现逻辑来维护和提升通信的可靠性，而无需依赖协议，但协议层提供的支持无疑是一个额外的优势。

保持连接周期

MQTT协议是全双工的，具有实时通信功能，这意味着通信双方都必须保持连接并处于活动状态。在发布/订阅机制中，代理和客户端在通信时应保持连接并处于活动状态。如果由于任何原因（如网络不可靠等）导致连接中断，双方都应该知道发生了这种情况并采取相应的行动。

然而，MQTT所基于的基本TCP协议在实际应用中并不一定能完全做到这一点（理论上应该可以），这就可能导致一种称为半开连接的情况。为了解决这种情况，引入了保持连接（keep alive）机制。

保持连接周期是指客户端发送完一个控制数据包到开始发送下一个控制数据包之间允许的最大时间间隔。客户端有责任确保发送控制数据包的时间间隔不超过保持连接的值。如果在没有发送任何其他控制数据包的情况下，客户端必须发送一个PINGREQ数据包。（OASIS标准 - MQTT版本3.1.1，2015）

简而言之，如果客户端和代理之间的数据传输时间间隔小于保持连接周期指定的时间，连接将保持活动且完全可验证。如果没有数据传输，客户端则会发送一个两字节的传输（以PINGREQ数据包的形式），让代理知道它仍然在线。如果客户端在该时间间隔内既没有发送保持连接数据包也没有发送任何数据，代理将关闭连接并发布客户端在连接时设置的遗嘱消息（last - will message）。

虽然较短的保持连接周期似乎对数据质量/时效性/准确性有益，但如果发送过多不必要的消息，可能会适得其反。因为这可能会导致代理、网络和其他资源被用于处理这些开销，从而可能会减慢消息处理速度。

注意，保持连接的最大间隔为18小时12分钟15秒，即65,535秒。如果将保持连接间隔设置为0，则此机制将被禁用。

遗嘱消息

如前所述，当客户端未向代理发送保持连接数据包或任何数据时，连接将被关闭，代理会向所有订阅者发布一条特殊消息，称为遗嘱消息（last will and testament，LWT）。这使得所有其他订阅者和应用程序能够在客户端意外断开连接时做出相应的有意义的反应。

需要注意的是，“正常断开连接” 指的是任何设备或客户端通过适当的协议握手主动从消息代理断开连接。如果没有发生这种情况（即断开连接是由网络故障等外部因素导致的），代理会立即向所有订阅者发布LWT消息。

每当客户端建立新连接时，用于该连接的众多参数之一就是遗嘱消息。与客户端发布的任何其他消息一样，这是一条客户端消息，但有一个特殊之处，即除非客户端意外断开连接，否则它不会被发布。LWT是通知所有其他订阅者客户端断开连接并让它们做出相应反应的最佳方式。

保留消息

保留消息与客户端发布的其他消息类似。保留标志被设置为1或true，这会指示代理保留该消息的副本，直到它被删除或替换。每当有订阅者订阅与保留消息主题匹配的主题或模式时，该消息会立即被传递。

需要注意的是，每个主题只有一条保留消息，这为保持所有设备和应用程序了解其他所有内容的当前状态提供了一种有趣的方式。图6 - 1展示了我们如何建立这样一种机制。

在图6 - 1中，客户端A（一个温度传感器）首次连接到代理时，设置遗嘱消息为 “offline”，主题为 “temp - sensor/status”，并将保留标志设置为true。这告诉代理存储此消息，直到被客户端覆盖或删除，并且仅在温度传感器意外断开连接时发布该消息。建立连接后，传感器立即在同一主题 “temp - sensor/status” 上发布另一条消息 “online”，并将保留标志设置为true。

现在，任何新订阅 “temp - sensor/status” 的客户端都会始终收到 “online” 作为响应。然而，如果温度传感器断开连接，代理会发布其LWT消息，所有订阅者会立即收到 “offline” 消息。这使得其他所有客户端都能随时了解温度传感器的在线状态。或者，如果传感器想要主动断开连接，它可以首先在同一主题上发布一条 “disconnected” 消息，向所有客户端表明它已主动从代理断开连接。

带有LWT的保留消息是建立一种始终保持每个客户端状态更新的有效机制。

要从代理的存储中删除保留消息，只需在同一主题上发布一条空消息即可。例如，如果 “temp - sensor/status” 发布一条长度为0字节的字符串，并将保留标志设置为true，现有消息值将被覆盖，不再被保留。

最棒的部分：WebSocket

我们已经了解了MQTT在物联网通信中，尤其是在我们自己的物联网平台中的重要性和工作原理。因此，自然期望我们能够在使用该平台的基于浏览器的应用程序中利用这一功能。WebSocket使基于浏览器的应用程序能够使用所有MQTT功能，这在许多有趣且有用的实际应用场景中都非常实用。

然而，浏览器目前还不能直接与TCP通信，因此也无法直接与MQTT通信。我们需要利用浏览器现有的与WebSocket协议通信的能力。WebSocket是一种网络协议，它在浏览器和Web服务器之间提供双向通信。该协议于2011年标准化，几乎所有现代浏览器都提供内置支持。好处是WebSocket协议与MQTT一样，也是基于TCP的，这使得集成变得更加容易。

现代浏览器和HTML5引入了许多新功能，使我们能够构建出行为类似于桌面和移动应用程序的网站。渐进式Web应用程序（Progressive Web Apps，PWAs）就是一个典型的例子。浏览器几乎安装在所有设备上，如台式计算机、笔记本电脑、平板电脑或智能手机。

使用通用协议与异构设备和系统进行所有通信所带来的一致性，是在WebSocket上使用MQTT的最诱人的原因之一。在WebSocket上使用MQTT还使我们的应用程序能够通过实时双向通道进行通信。从实时多方聊天到实时监控和控制系统，应用场景数不胜数。在本书后面的内容中，一旦平台的大部分功能构建完成并准备就绪，我们将启用并实现基于WebSocket的MQTT通信。

我们使用的是最佳的消息代理选项吗？

有几种开发具有全双工功能和各种支持特性的消息代理的选项，其中一些包括使用原始TCP套接字、原始UDP套接字、AMQP和CoAP。与MQTT相比，这些替代方案大多存在更多的限制和复杂性，而优势相对较少。这就是为什么MQTT成为构建我们自己的物联网平台时最合适、高效和方便的选择。

请记住，所有这些协议都可以共存，并且如果需要，我们可以在同一云实例上部署它们。这意味着在未来，如果你决定同时使用AMQP和MQTT，是可以实现集成的。更重要的是，我们可以通过额外的插件程序将这些通道连接起来，以便从应用程序和设备的角度实现无缝通信。虽然这超出了本书的范围，但确实是可行的。

何时使用消息代理以及何时不使用

从根本上讲，MQTT是一种异步协议，因此能够实现具有轻量级系统负担的双工通信。它允许系统在低带宽和低功耗条件下运行。相比之下，HTTP和类似协议需要相对较高的带宽和功率，并且本质上是请求 - 响应式的，这意味着客户端必须始终发起通信。

在希望任何一方（服务器或客户端）都能发起通信的场景中，MQTT是最佳选择。此外，如果系统需要在低数据消耗（特别是依靠电池供电）的情况下长时间运行，使用MQTT是明智的选择。如果设备需要频繁且随机地发送或接收数据，那么MQTT也很合适，因为它可以显著减少HTTP的开销。

如果带宽和功率不是问题，那么HTTP可能是更好的选择。另外，当数据发送或接收的频率不高时，使用HTTP也可以，因为在这种情况下，HTTP不会很快阻塞资源。

在需要实时控制或监控的应用中，MQTT显然是首选，因为它提供双工和双向通信能力，且开销最小。

你必须注意，基于MQTT的系统的工作量可能会呈抛物线式增长，这意味着对于每个添加到使用MQTT进行通信的网络中的设备（假设网络中总共有n个设备），系统的负载将变为n的平方（n * n）。图6 - 2以图形方式解释了这个概念。

例如，假设一个极端情况，有两个客户端，每个客户端都订阅了所有可能的主题（通配符#）。当一个客户端发布一条消息时，代理需要接收该消息，并且另一个客户端也需要接收该消息。这意味着发送一条消息可能会导致两次传输。对于另一个客户端也是如此，因此对于一个包含两个客户端的系统，总共会产生四条消息。对于一个包含三个客户端的系统，这个数字会变为九条消息（即每个客户端三条消息）。仅仅连接100个设备就意味着消息代理应该能够处理10 * 10（即100条消息），以此类推。

这意味着当客户端数量开始增加时，消息代理和整个系统（以及平台）的负载将几乎呈指数级增长；在我们后期扩展物联网平台时，需要牢记这一点。

为我们的平台创建第一个流程

完成所有必要设置后，流程序列如图7 - 8所示。部署此序列后，时间戳注入开始，并且每隔15秒重复一次。时间戳的输出被发送到两个节点：调试节点和mqtt out节点。调试节点会在调试侧边栏中显示注入的时间戳，而mqtt out节点会将这个时间戳以“timestamp”为主题，以当前UNIX微秒时间戳的值（例如1543677926496）推送到消息流中。

创建数据库监听器

数据库监听器本质上是一种机制，通过某个程序或函数监听实时消息流，并将监听到的所有内容存储到数据库中。在我们的场景中，我们已经通过MQTT建立了一个实时消息流。现在我们将构建一个功能，使我们的程序流程能够监听MQTT流，并将所有消息记录到时间序列数据库中。

为此，我们从输入调色板中将mqtt输入节点添加到工作区，然后添加调试节点并将其连接到mqtt输入节点。这是最简单的流程序列，因为实际上我们只有一项需要配置。注意，MQTT代理的详细信息已经添加过了。

WebSocket与普通MQTT的区别

WebSocket提供了一个始终保持打开的通信通道，这与普通HTTP不同，HTTP的通道会在每次请求时打开和关闭。WebSocket提供了双向通信通道，但它不一定遵循MQTT协议。你可以实现一个原始的WebSocket，并让两个设备通过它进行通信。

在WebSocket之上使用MQTT增加了强大的功能。它使WebSocket客户端能够通过消息订阅选择自己想要接收的内容。它还增加了一种能力，即客户端可以通过代理向其他多个客户端发布消息或信息，而在正常情况下，使用基本的WebSocket通信来实现这一点会很繁琐。除此之外，MQTT的其他特性，如保留消息、服务质量（QoS）、遗嘱消息（LWT）等，使其更加出色。

WebSocket为何重要？

从我们自己的物联网平台角度来看，提供多种将平台连接到各种设备的方法是一项基本要求。这就是为什么我们选择了HTTP REST接口和MQTT来实现这一目的。然而，由于这两种协议和技术都有各自的优缺点，能够将它们结合起来会显著提升应用架构。

想象一下，如果你的Web应用程序能够与所有其他应用程序用户以及连接到平台的设备进行实时通信，它将获得多大的优势。通过使Web应用程序能够直接从浏览器控制这些设备，WebSocket为Web应用程序带来的强大功能，就是在MQTT上启用WebSocket的充分理由。

此外，所有系统和设备都可以使用MQTT和/或HTTP进行通信，并从我们集成到物联网平台的所有功能中受益。

添加用户访问控制

在配置MQTT代理时，我们禁止了匿名登录，通过强制提供用户名和密码的方式在一定程度上保护了它。然而，这并不能阻止合法用户窥探彼此的数据。此外，任何人都可以发布或接收任何内容，这是不可接受的。

这就是为什么MQTT有另一种配置设置，称为访问控制列表（ACL）。通过使用ACL，我们可以为每个用户或客户端控制对主题的访问。我们本质上希望只允许授权的发布者发布特定主题的消息，并允许授权的订阅者收听这些广播。

第一部分是通用设置。在这里，我们给予普通用户对timestamp及其子主题的读取权限。请记住，我们在平台上完全禁止了匿名连接，这意味着这部分设置实际上永远不会被使用。

第二部分定义了两个用户的设置。第一个用户名为admin，对所有主题（即“#”）具有读写权限。第二个用户名为my_app_name，对我们的timestamp主题具有读取权限。此外，对于myapp/%c/#主题，该用户具有完全的读写访问权限。这意味着任何以my_app_name用户名和唯一客户端ID（例如device_1或类似名称）连接的客户端，都能够在myapp/device_1/#上进行读写操作。通过这种方式，我们可以在myapp应用程序域内隔离所有客户端。在这里，任何连接的客户端都不能在定义的主题之外的其他主题上发布消息，并且只能订阅timestamp主题。

最后一部分定义了基于模式的设置。同样，我们定义所有没有上述用户名的客户端都能够订阅timestamp主题。

此外，我们允许所有客户端在由users/%u/#模式定义的用户特定主题上进行发布或订阅，允许他们在%c/up/#上进行发布，在%c/dn/#上进行订阅。这意味着如果一个ID为device_1的客户端以foo_bar用户名连接，那么它能够在users/foo_bar/#上进行发布和订阅，在device_1/up/#上进行发布，并在device_1/dn/#上进行订阅。任何其他不符合给定模式的发布或订阅请求都将不被允许。

用户名 - 密码组合可以被多个应用程序和/或设备重复使用；因此，对用户设置的任何更改都会影响到所有使用该组合的应用程序和设备。一般来说，客户端ID在连接到代理时必须是唯一的。因此，基于客户端ID的模式设置中的任何访问控制都仅适用于单个客户端。

请注意，主题名称、用户名和客户端名称通常是区分大小写的；不仅在ACL中如此，在整个MQTT范式中都是如此。

模式设置和通用设置是累加的。这意味着如果模式设置不允许某个操作，但通用设置允许，那么代理将允许该操作。

模式设置优先于用户设置。因此，如果模式设置允许客户端订阅或发布某个主题，那么无论用户设置如何，代理都会允许。

由于我们在连接到消息代理时强制要求用户名和密码，可能会出现以下几种情况：

  • 情况1

    • 通用设置 = 空白或已配置

    • 用户设置 = 空白

    • 模式设置 = 空白

    • 结果是所有主题的访问都被拒绝。

  • 情况2

    • 通用设置 = 空白或已配置

    • 用户设置 = 已配置

    • 模式设置 = 空白

    • 结果取决于用户设置，代理会忽略通用设置。

  • 情况3

    • 通用设置 = 空白或已配置

    • 用户设置 = 空白或已配置

    • 模式设置 = 已配置

    • 结果是模式设置优先于用户设置。

从规则引擎逻辑入手

构建规则引擎基础设施的方式有很多种，并没有绝对的对错之分，只有是否巧妙、是否高效的区别。同时，规则引擎的价值与其所能提供的简洁性以及达成预期结果的能力直接相关。如果为了实现结果需要构建过多的东西，那么这种构建的价值就会降低。

基于此，我们可以通过两种方式构建规则引擎。一种是利用Node - RED基于流程的方法，简单添加一个消息流监听器，它可以根据预先编程的标准将消息分发给其他多个节点，然后执行进一步的操作。这里的关键词是“预先编程”。这意味着在部署规则之前，我们总是需要手动预先编写规则，这种方式在一定程度上比较僵化。要是我们需要动态添加新规则，或者根据其他规则的输出激活或停用现有规则该怎么办呢？这些情况促使我们采用另一种方法：基于查询的规则。这就是我们现在要构建的内容。

创建数据库

构建基于查询的规则引擎的第一步是定义数据模式，并在我们的时间序列数据存储中添加一个数据表。让我们创建这个规则表，如图10 - 1所示。

我们将其命名为ruleEngine表。在这个数据表中，我们有一个主键且值自动递增的id字段，这是后续引用任何规则所必需的。ruleName是规则的可读名称。active列是二进制类型，用于定义规则是否处于激活状态。有两个列定义了规则的逻辑：topicPattern和payloadPattern。这些列包含类似SQL的模式，用于规则匹配；基于匹配结果，我们可以使用webHook字段的值，并按照method列中定义的方法进行调用。默认情况下，method设置为GET请求。

我们可以基于这个结构进行多种扩展。比如，添加更多列来存储各种其他要执行的操作、要更改的值、要执行的脚本，或者受影响的全局变量等。我们也可以将这些操作放在webHook URL指向的另一个Web服务或脚本文件中，这样更为简洁。

由此产生的一个明显问题是，我们如何有效地为物联网平台的API编写文档呢？最受欢迎的方法之一是使用免费或开源工具来进行API文档编写。

我们将使用Swagger工具来生成API文档。使用Swagger可以轻松创建交互式文档，并且在后续维护过程中也毫不费力。更重要的是，你既可以将接口（定义和沙盒）托管在Swagger hub上，也可以将其作为独立组件集成到单独的云实例中。我们在本书中采用的就是后者。

准备有效的OpenAPI规范文档

创建有用文档的第一步是使用有效的格式创建API描述文档。由于Swagger使用OpenAPI规范，且该规范可以用YAML格式进行文档编写，所以我们首先要创建YAML格式的文档。

YAML（YAML Ain’t Markup Language）是一种人类可读的数据序列化语言，通常用于配置文件，也可用于许多数据存储（如调试输出）或传输（如文档头）的应用场景。

如果你对学习OpenAPI格式和规范感兴趣，互联网上有很多教程，Swagger网站上也有不少。

Swagger在线编辑器是另一个开源免费工具，可用于验证我们正在准备的规范文档，或者我们也可以在该编辑器中从头开始创建文档。该编辑器的网址是https://editor.swagger.io/#/ 。

在撰写本书时，我创建了一个API规范文档（api.yml），你可以从GitHub上获取。下载该文件（.yml格式，即YAML格式），将文件内容粘贴到Swagger在线编辑器中，确保没有警告或错误。在Swagger编辑器右侧的视图中，你看到的是部署后的实际用户界面。

你可以对文档进行修改，看看这些修改如何影响输出结果。完成后，将文件内容复制并粘贴回本地副本，以便进一步使用。

部署选项

在部署物联网平台时，我们有多种选择，每种选择都有其优缺点。以下是一些常见的部署选项：

  • 裸机服务器：在裸机服务器上直接部署平台意味着你拥有对硬件和软件的完全控制权。你可以根据自己的需求进行定制化配置，安装所需的操作系统和软件包。然而，这种方式需要更多的技术知识和管理工作，包括服务器的维护、硬件的升级等。

  • 虚拟专用服务器（VPS）：VPS 是一种虚拟化的服务器，它提供了独立的计算资源，如 CPU、内存和存储。与裸机服务器相比，VPS 的管理相对简单，你可以通过控制面板轻松地进行配置和管理。同时，VPS 的成本通常比裸机服务器低。

  • 云服务提供商：使用云服务提供商（如 Amazon Web Services、Google Cloud Platform 或 Microsoft Azure）可以让你轻松地部署和扩展平台。这些云服务提供商提供了各种服务，如计算、存储、数据库等，你可以根据自己的需求选择合适的服务。此外，云服务提供商还提供了高可用性和容错能力，确保平台的稳定运行。

  • 容器化部署：容器化部署是一种轻量级的虚拟化技术，它将应用程序及其依赖项打包成一个独立的容器。容器可以在不同的环境中运行，确保应用程序的一致性和可移植性。Docker 是最流行的容器化平台之一，我们将在后面的章节中详细介绍如何使用 Docker 进行部署。

使用 Docker 进行容器化部署

Docker 是一个开源的容器化平台，它可以帮助我们将应用程序及其依赖项打包成一个独立的容器。使用 Docker 进行部署有以下优点：

  • 一致性：容器包含了应用程序运行所需的所有依赖项，确保在不同的环境中都能一致运行。

  • 可移植性：容器可以在任何支持 Docker 的环境中运行，包括开发、测试和生产环境。

  • 快速部署：容器的启动和停止速度非常快，可以实现快速的部署和更新。

  • 资源隔离：容器之间相互隔离，不会相互影响，提高了系统的安全性和稳定性。

平台的扩展策略

随着物联网设备数量的增加和数据流量的增长，我们需要考虑如何对平台进行扩展以满足不断增长的需求。以下是一些常见的扩展策略：

  • 水平扩展：水平扩展是指通过增加服务器的数量来提高平台的处理能力。你可以使用负载均衡器将请求分发到多个服务器上，从而实现水平扩展。例如，使用 Nginx 或 HAProxy 作为负载均衡器。

  • 垂直扩展：垂直扩展是指通过增加单个服务器的硬件资源（如 CPU、内存和存储）来提高平台的处理能力。这种方式相对简单，但成本较高，并且有一定的限制。

  • 数据库扩展：数据库是物联网平台的核心组件之一，随着数据量的增加，数据库的性能可能会成为瓶颈。你可以考虑使用分布式数据库（如 Cassandra 或 MongoDB）来实现数据库的扩展。

  • 缓存机制：使用缓存机制可以减少对数据库的访问，提高平台的响应速度。你可以使用 Redis 或 Memcached 作为缓存服务器。

术语表

  • API（Application Programming Interface）：应用程序编程接口。一组用于构建软件应用程序的规则和协议，允许不同的软件组件或系统之间进行交互和通信。

  • AES（Advanced Encryption Standard）：高级加密标准。一种广泛使用的对称加密算法，用于保护数据的机密性。

  • Bearer Authentication：令牌认证。一种使用令牌（通常是 JWT）来验证用户身份和授权访问资源的认证方式。

  • Cloud - Agnostic：云无关性。指系统或应用程序不依赖于特定的云服务提供商，可以在不同的云环境中运行。

  • CryptoJS：一个 JavaScript 库，用于实现各种加密算法，如 AES、SHA - 256 等。

  • Docker：一个开源的容器化平台，用于将应用程序及其依赖项打包成独立的容器，实现应用程序的快速部署和可移植性。

  • JWT（JSON Web Token）：JSON Web 令牌。一种开放标准（RFC 7519），用于在各方之间安全地传输声明。它通常由三部分组成：头部、载荷和签名。

  • LoRaWAN：一种低功耗广域网（LPWAN）协议，用于物联网设备的长距离通信。

  • Middleware：中间件。位于操作系统和应用程序之间的软件层，提供各种服务和功能，如数据传输、协议转换、安全认证等。

  • Node - RED：一个基于流的编程工具，用于连接硬件设备、API 和在线服务。它使用可视化的节点和流来创建应用程序逻辑。

  • OpenAPI Specification：OpenAPI 规范。一种用于描述 RESTful API 的标准格式，通常使用 YAML 或 JSON 编写。它可以用于生成 API 文档、测试工具和客户端代码。

  • REST（Representational State Transfer）：表述性状态转移。一种软件架构风格，用于设计网络应用程序的 API。RESTful API 使用 HTTP 协议进行通信，通过不同的 HTTP 方法（如 GET、POST、PUT、DELETE）来操作资源。

  • Swagger：一个用于设计、构建、记录和使用 RESTful API 的开源工具集。它可以根据 OpenAPI 规范生成交互式的 API 文档，并提供测试和调试功能。

  • Time - Series Database：时间序列数据库。一种专门用于存储和管理时间序列数据的数据库，适用于物联网、监控和日志分析等场景。

  • UUID（Universally Unique Identifier）：通用唯一识别码。一种由数字和字母组成的 128 位标识符，用于在分布式系统中唯一地标识资源。

  • WebHook：一种 Web 回调机制，当特定事件发生时，服务器会自动向预先注册的 URL 发送 HTTP 请求，通知其他系统或应用程序。

  • YAML（YAML Ain’t Markup Language）：一种人类可读的数据序列化语言，常用于配置文件和数据交换。它的语法简洁，易于阅读和编写。
